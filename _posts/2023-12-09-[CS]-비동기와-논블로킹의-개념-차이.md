## 비동기와 논블로킹의 개념적 차이

Apache Livy의 REST API와 PostgreSQL 비동기 라이브러리인 asyncpg를 사용하면서 비동기와 논블로킹을 구분할 필요를 느꼈다. 둘 다 비동기 방식이라고 생각했는데 작업 결과를 받는 방식은 달랐다.

Livy에서는 작업을 제출하고 ID를 받은 뒤 나중에 결과를 조회할 수 있었다. asyncpg에서는 `await`로 쿼리 결과를 기다렸다. 기다린다는 표현은 같아도 어디에서 무엇을 기다리는지 구분해야 한다.

### 동기와 비동기

동기 호출은 작업의 결과가 호출의 반환에 연결된다. 호출자는 그 결과를 받은 뒤 다음 처리를 진행한다. 다만 동기라고 해서 프로그램 전체가 한 번에 작업 하나만 실행한다는 뜻은 아니다. 다른 스레드나 프로세스에서는 별도의 작업을 할 수 있다.

비동기 작업은 시작과 완료 처리를 분리할 수 있다. 콜백이나 Future, 코루틴 같은 방식으로 나중에 완료를 확인하고 결과를 받는다. 시작 순서와 완료 순서가 꼭 같을 필요는 없지만 항상 순서가 뒤섞여야 하는 것도 아니다.

### 블로킹과 논블로킹

블로킹 호출은 결과나 자원이 준비될 때까지 호출한 스레드를 대기시킨다. 예를 들어 일반적인 소켓 수신은 읽을 데이터가 없으면 기다릴 수 있다.

논블로킹 호출은 지금 처리할 수 없다면 그 상태를 알리고 반환한다. 소켓에서는 `BlockingIOError`처럼 아직 읽을 수 없다는 결과를 받을 수 있다. 이후 다시 시도할 시점을 정하려면 이벤트 루프나 준비 상태 알림 같은 방식이 필요하다.

| 구분 | 확인할 질문 |
|---|---|
| 동기·비동기 | 작업의 시작과 완료 처리가 분리되어 있는가? |
| 블로킹·논블로킹 | 호출한 스레드가 준비되지 않은 결과 때문에 멈추는가? |

`await`로 결과를 기다리는 것과 스레드를 블로킹하는 것도 구분해야 한다. `await` 중에는 현재 코루틴이 중단될 수 있지만 이벤트 루프는 다른 코루틴을 실행할 수 있다.

## Apache Livy와 asyncpg의 차이

### Apache Livy: 작업 제출과 결과 조회를 분리

Livy는 Spark 작업을 제출하고 상태와 결과를 조회할 수 있는 REST API를 제공한다. 예를 들어 세션에 statement를 제출한 뒤 반환받은 ID로 상태와 출력을 조회할 수 있다.

1. `POST /sessions/{sessionId}/statements`로 코드를 제출한다.
2. 응답에서 statement ID를 받는다.
3. `GET /sessions/{sessionId}/statements/{statementId}`로 상태와 결과를 확인한다.

작업 실행이 끝날 때까지 처음 HTTP 요청을 계속 붙잡아 두지 않는 구성이다. 그렇다고 Livy를 호출한 클라이언트의 HTTP 코드까지 자동으로 논블로킹이 되는 것은 아니다. `requests.post()`로 호출하면 그 HTTP 응답을 받는 동안 호출한 스레드는 기다린다.

### asyncpg: 쿼리를 기다리는 동안 다른 코루틴 실행

asyncpg는 `asyncio`를 사용하는 PostgreSQL 클라이언트다. `await connection.fetch(...)`는 쿼리 결과를 기다리는 동안 다른 코루틴이 실행될 수 있도록 한다.

연결 하나에서 여러 쿼리를 동시에 실행할 수 있다는 뜻은 아니다. 쿼리를 겹쳐 실행하려면 풀에서 별도의 연결을 얻어 각 작업에 사용해야 한다. 같은 연결에서는 앞선 작업을 마친 뒤 다음 작업을 실행한다.

asyncpg를 사용하는 HTTP API가 쿼리를 끝낸 뒤 응답하도록 만들면 사용자는 최종 결과가 나올 때까지 기다린다. 그 시간 동안 서버의 이벤트 루프가 다른 요청을 처리할 수 있다는 것과 HTTP 응답이 아직 오지 않았다는 것은 별개의 문제다.

### 연결 풀로 여러 쿼리 실행하기

다음은 연결 풀에서 각자 연결을 얻어 두 작업을 실행하는 예시이다. `asyncpg` 설치와 접속 가능한 PostgreSQL이 필요하며 접속 문자열은 자신의 환경에 맞게 바꾼다.

```python
import asyncio
import asyncpg

async def read_value(pool, value):
    async with pool.acquire() as connection:
        return await connection.fetchval("SELECT $1::integer", value)

async def main():
    async with asyncpg.create_pool(
        "postgresql://USER:PASSWORD@localhost/DB_NAME",
        min_size=1,
        max_size=2,
    ) as pool:
        values = await asyncio.gather(
            read_value(pool, 1),
            read_value(pool, 2),
        )
        print(values)  # [1, 2]

asyncio.run(main())
```

`gather()`는 두 코루틴을 실행 대상으로 등록하고 `pool.acquire()`는 각 작업에 연결을 빌려준다. 빌릴 연결이 없다면 해당 코루틴이 기다린다. 쿼리가 끝나 `async with` 블록을 벗어나면 연결을 풀에 돌려준다.

연결 수를 늘리면 DB에 동시에 보내는 쿼리 수도 늘 수 있다. 이벤트 루프를 막지 않는다고 DB의 처리 용량까지 늘어나는 것은 아니므로 풀 크기도 DB가 감당할 수 있는 범위에서 정해야 한다.

## 내 API에서는 무엇을 분리할까?

조회가 짧게 끝나는 API라면 결과를 받은 뒤 HTTP 응답을 반환해도 된다. 이 응답을 기다리는 클라이언트도 비동기 HTTP 클라이언트를 사용하면 자신의 스레드를 블로킹하지 않을 수 있다.

작업이 오래 걸리고 클라이언트가 나중에 결과를 다시 확인해야 한다면 작업 ID와 상태 조회 API를 두는 방식을 고려할 수 있다. 필요에 따라 큐와 별도 워커를 사용하지만 asyncpg를 쓴다는 이유만으로 RabbitMQ가 필요한 것은 아니다. 이런 구성에서는 HTTP 응답 이후에도 작업을 유지할 저장소와 재시도 방식까지 정해야 한다.

## 마무리

Livy는 작업 제출과 결과 조회를 API 수준에서 나눈 예시이고 asyncpg는 DB 응답을 기다리는 동안 이벤트 루프가 다른 일을 할 수 있게 하는 예시다. 비동기 라이브러리를 사용하더라도 작업 ID를 바로 돌려줄지와 최종 결과까지 기다린 뒤 응답할지는 API에서 따로 정해야 한다.
