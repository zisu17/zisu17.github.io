## WAL은 무엇을 기록할까?

[앞선 글](/data/[CDC]-WAL-기반-CDC-파이프라인-구축-1/)에서는 PostgreSQL의 변경을 Debezium과 Kafka로 전달하는 흐름을 정리했다. 이번에는 변경을 읽을 수 있도록 DB 쪽 설정을 확인하려고 한다.

WAL(Write-Ahead Log)은 장애가 나도 DB를 일관된 상태로 복구하기 위한 로그이다. 변경된 데이터 페이지를 데이터 파일에 쓰기 전에 그 변경을 복구할 WAL 기록을 먼저 디스크에 남기는 것이 기본 원칙이다.

“SQL을 실행하기 전에 모든 로그를 먼저 쓴다”는 뜻은 아니다. 메모리에서 변경을 처리하는 과정과 데이터 파일에 반영하는 시점을 구분해야 한다. 기본적인 동기 커밋에서는 커밋 성공을 알리기 전에 필요한 WAL이 디스크에 기록되기를 기다린다. 변경된 데이터 페이지 전체가 데이터 파일에 기록될 때까지 기다리는 것은 아니다.

CDC에서는 이 WAL을 논리 디코딩해 행의 삽입과 수정, 삭제 정보를 얻는다. 바이너리 WAL 파일을 단순히 텍스트로 읽는 방식과는 다르다.

## 먼저 현재 설정 확인하기

아래 설명은 PostgreSQL 16 문서를 기준으로 한다. 서버 버전과 실제 설정은 먼저 조회한다. 관리형 DB에서는 설정 파일을 직접 편집하는 대신 파라미터 그룹 같은 별도 기능을 사용할 수 있다.

```sql
SHOW server_version;
SHOW config_file;

SELECT name, setting, unit, context, pending_restart
FROM pg_settings
WHERE name IN (
    'wal_level',
    'max_wal_senders',
    'max_replication_slots',
    'max_slot_wal_keep_size',
    'wal_sender_timeout'
)
ORDER BY name;
```

`setting`이 현재 적용값이고 `pending_restart`는 설정 변경 후 재시작이 필요한 상태인지 보여준다. 파일만 바꾸고 이미 적용됐다고 판단하지 않는다.

## 논리 디코딩을 위한 설정

| 설정 | 역할 | 확인할 점 |
|---|---|---|
| `wal_level` | WAL에 남길 정보 수준 | 논리 디코딩에는 `logical` 필요 |
| `max_wal_senders` | 동시에 실행할 WAL 전송 프로세스 수 | 물리 복제와 다른 복제 클라이언트까지 고려 |
| `max_replication_slots` | 생성 가능한 복제 슬롯 수 | 기존 슬롯과 새 Connector가 사용할 슬롯 고려 |
| `wal_sender_timeout` | 응답 없는 복제 연결을 끊는 기준 | 로그 보관 기간이 아님 |
| `max_slot_wal_keep_size` | 슬롯이 보관하게 할 WAL의 용량 제한 | 필요한 WAL이 지워지면 이어 읽기 실패 가능 |

`postgresql.conf`의 설정 예시는 다음과 같다. 10은 예제 값이지 CDC에 항상 필요한 최소값은 아니다. 기존 설정과 연결 수를 확인하고 정해야 한다.

```ini
wal_level = logical
max_wal_senders = 10
max_replication_slots = 10
```

위 세 항목은 PostgreSQL 16에서 서버 재시작이 필요하다. 재시작 후 앞선 쿼리로 실제 적용값을 확인한다. 기존에 사용 중인 슬롯 수보다 `max_replication_slots`를 작게 줄이면 서버 시작에 문제가 생길 수 있다.

### wal_level의 차이

`minimal`은 장애 복구에 필요한 기본 정보만 남기며 일반적인 스트리밍 복제와 논리 디코딩에 사용할 수 없다. `replica`는 물리 복제와 아카이빙 등에 필요한 정보를 남긴다. `logical`은 여기에 행의 논리적 변경을 추출할 정보를 더한다.

`logical`로 설정한다고 Connector와 복제 슬롯이 자동으로 만들어지는 것은 아니다. 접속 계정의 권한과 대상 테이블, publication도 별도로 준비해야 한다.

Debezium에서 `pgoutput`을 사용하는 경우에는 복제 연결 권한과 초기 스냅샷에 필요한 테이블 조회 권한을 확인한다. publication을 자동으로 만들지와 미리 만들어 사용할지도 정한다. 서버 설정과 계정 권한은 다른 단계이다.

수정과 삭제를 전달하려면 대상 행을 식별할 정보도 필요하다. 기본 키가 없는 테이블은 `REPLICA IDENTITY` 설정을 확인한다. 무조건 `FULL`로 바꾸기보다 필요한 변경 정보와 WAL 증가량을 함께 검토해야 한다.

## 복제 슬롯이 필요한 이유

복제 슬롯은 변경을 읽는 클라이언트가 필요한 위치를 PostgreSQL에 남기는 장치이다. 연결이 끊어졌다고 바로 사라지지 않는다. 서버는 슬롯이 아직 필요로 하는 WAL을 쉽게 지우지 않도록 관리한다.

예를 들어 Connector가 오후 1시 위치까지 처리하고 중단되면 이후 변경을 이어 읽을 수 있어야 한다. 이때 슬롯이 필요한 WAL을 보관하게 한다. 다만 DB의 WAL 위치인 LSN(Log Sequence Number)과 Kafka 토픽의 오프셋은 서로 다른 값이다.

### Connector가 멈추면 디스크가 찰 수 있다

Connector가 중단되어도 DB에서 변경이 계속 발생하면 WAL이 쌓일 수 있다. 복구를 위해 필요한 로그를 보관하는 기능이 오히려 디스크 사용량 증가로 이어지는 것이다.

```sql
SELECT slot_name,
       plugin,
       slot_type,
       active,
       restart_lsn,
       confirmed_flush_lsn,
       pg_size_pretty(
           pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)
       ) AS lsn_distance
FROM pg_replication_slots
WHERE slot_type = 'logical';
```

`restart_lsn`은 슬롯이 필요로 할 수 있는 가장 오래된 WAL 위치이고 `confirmed_flush_lsn`은 논리 복제 클라이언트가 수신을 확인한 위치이다. 위의 차이는 로그 보관 압력을 살펴보는 지표이지 `pg_wal` 디렉터리의 실제 사용량과 정확히 같은 값은 아니다.

`active=false`라는 이유만으로 바로 슬롯을 삭제해서는 안 된다. 일시적으로 끊긴 Connector가 다시 사용할 수도 있다. 슬롯을 삭제하면 그 위치에서 이어 읽는 데 필요한 보관 기준도 사라지므로 사용처와 복구 계획을 먼저 확인한다.

### WAL 용량 설정은 하드 제한일까?

`max_wal_size`는 체크포인트와 WAL 관리에 사용하는 기준값이지 디렉터리 용량의 절대 상한이 아니다. 복제 슬롯이나 아카이빙 지연 때문에 더 많은 WAL이 남을 수 있다.

`max_slot_wal_keep_size`로 슬롯의 WAL 보관량을 제한할 수 있지만 필요한 로그가 제거되면 Connector가 이어 읽지 못할 수 있다. 디스크 보호와 중단 후 복구 가능 시간을 함께 고려해야 한다.

또 오래된 설정의 `wal_keep_segments`는 PostgreSQL 13부터 `wal_keep_size`로 바뀌었다. 이 값도 슬롯별 로그 보관과 동일한 기능으로 취급하면 안 된다.

## 복구 설정과 CDC 설정 구분하기

`fsync`와 `full_page_writes`는 장애 복구와 데이터 안전성에 관련된 설정이다. CDC를 붙인다는 이유로 끄지 않는다.

`synchronous_commit`은 커밋 성공을 알리기 전에 어느 수준까지 WAL 처리를 기다릴지 정한다. “변경한 테이블 파일 전체를 디스크에 쓸 때까지 기다리는 설정”은 아니다.

아카이빙과 특정 시점 복구 설정도 논리 디코딩을 켜는 설정과는 목적이 다르다. 모든 WAL 관련 옵션을 한꺼번에 바꾸기보다 필요한 항목과 현재 값을 먼저 확인하는 편이 좋다.

## pg_waldump와 논리 디코딩의 차이

`pg_waldump`는 WAL 레코드를 사람이 볼 수 있는 형태로 출력하는 진단 도구이다. 일반적인 테이블의 `SELECT` 결과나 CDC 행 이벤트를 만들어주는 도구는 아니다.

```bash
pg_waldump -p /path/to/copied-wal WAL_SEGMENT_NAME
```

예제의 경로와 파일명은 실제 확인할 WAL 세그먼트로 바꾼다. 서버 버전에 맞는 도구를 사용하고 실행 중인 서버의 파일은 출력이 일관되지 않을 수 있다는 공식 문서의 주의사항을 확인한다. 운영 DB의 파일을 직접 수정하거나 삭제해서는 안 된다.

Debezium은 PostgreSQL의 논리 디코딩과 복제 프로토콜을 사용해 변경 이벤트를 받는다. Connector를 붙이기 위해 `pg_waldump`로 파일을 직접 해석할 필요는 없다.

## 마무리

CDC 준비에서는 `wal_level`과 복제 연결·슬롯 수를 먼저 확인한다. 운영 중에는 Connector 상태뿐 아니라 슬롯의 처리 위치와 WAL 디스크 사용량도 함께 봐야 한다. 로그가 남아 있어야 중단 지점부터 복구할 수 있지만 무제한으로 남겨둘 수는 없기 때문이다.
