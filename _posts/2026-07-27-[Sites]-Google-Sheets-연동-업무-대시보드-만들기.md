## 1. 이 글의 목적

데이터를 관리하는 작은 조직에서는 Google Sheets가 데이터 입력 도구로 충분한 경우가 많다. 하지만 전체 진행률, 상태별 분포, 담당자별 업무량을 시트만으로 한눈에 파악하기는 어렵다.

이 글에서는 **ChatGPT Sites를 이용해 Google Sheets 연동 업무 대시보드를 만드는 과정**을 다룬다. 직접 프런트엔드 프로젝트를 처음부터 구성하는 방법보다, Sites에 어떤 요구사항을 전달하고 Preview에서 무엇을 확인하며 수정과 배포를 어떻게 반복하는지에 초점을 맞춘다.

본문의 조직명, 담당자명, 문서 주소, API 주소, 필드명은 모두 일반화한 예시 값이다. 실제 서비스의 식별정보는 포함하지 않는다.

```text
업무 요구사항 작성
→ Sites에서 첫 화면 생성
→ Google Sheets 조회 API 연결
→ Preview 검토
→ 후속 수정 요청
→ Publish
```

## 2. 왜 Sites로 만드는가

Sites는 대시보드의 요구사항을 자연어로 전달하면 실행 가능한 사이트를 만들고, Preview와 Publish까지 한 흐름에서 처리할 수 있다. UI 구현 경험이 적어도 화면 구조와 업무 규칙을 설명할 수 있다면 시작할 수 있다.

이 방식에서 사용자의 역할은 코드를 한 줄씩 지시하는 것이 아니다. **업무 화면이 지켜야 할 규칙을 구체적으로 정의하고 결과를 검수하는 것**이다.

| 직접 구현 중심 접근 | Sites 중심 접근 |
|---|---|
| 프로젝트 구조와 라이브러리를 먼저 결정한다 | 필요한 화면과 동작을 먼저 설명한다 |
| 컴포넌트 단위로 코드를 작성한다 | Sites가 초안을 만들고 수정 요청으로 다듬는다 |
| 로컬 실행과 배포 환경을 직접 구성한다 | Sites의 Preview와 Publish 흐름을 사용한다 |
| 기술 선택이 주요 의사결정이다 | 업무 규칙과 검수 기준이 주요 의사결정이다 |

> "Sites에 대시보드를 만들어 달라고 한 문장만 입력하면 끝나는가?"

그렇지 않다. 화면은 생성할 수 있지만 데이터 구조, 필터 해제 조건, 로딩 상태처럼 눈에 잘 보이지 않는 규칙은 빠질 수 있다. 첫 요청에 핵심 구조를 담고, 이후에는 현재 Preview를 기준으로 원하는 변경과 유지 조건을 설명해야 한다.

## 3. 만들기 전에 데이터 흐름부터 정한다

Sites에 화면을 요청하기 전에 데이터가 어디서 오고 어떤 형태로 전달되는지 정해야 한다. 예시 대시보드에서는 비공개 Google Sheets를 원본으로 사용하고, Apps Script Web App이 조회 API 역할을 한다.

```text
Google Sheets
└─ Apps Script Web App
   └─ Sites 대시보드
      ├─ 업무 현황 요약
      ├─ 상태별 원형 차트
      ├─ 담당자별 누적 막대
      └─ 고객 목록
```

브라우저가 비공개 시트를 직접 읽게 만들기보다 Apps Script가 서버 측에서 시트를 열고 JSON으로 반환하게 한다.

```text
브라우저가 /exec를 GET
→ Google이 doGet() 실행
→ SpreadsheetApp으로 비공개 시트 조회
→ 2차원 배열을 객체 배열로 변환
→ JSON 응답 반환
```

예시 응답 구조는 다음과 같이 단순하게 유지한다.

```json
{
  "ok": true,
  "rows": [
    {
      "담당자": "김담당",
      "구분": "정기 업무",
      "사업장": "예시상사",
      "업무상태": "작업 완료",
      "금액": "120,000원"
    }
  ]
}
```

첫 생성 요청에는 API 주소만 넣지 말고, **응답 모양과 화면 필드의 연결 관계**도 같이 적는다.

| API 필드 | 화면에서 사용할 위치 |
|---|---|
| `사업장` | 고객사명 |
| `담당자` | 담당자명과 담당자별 집계 |
| `업무상태` | 상태 태그와 원형 차트 |
| `구분` | 고객 목록의 구분 열 |
| `금액` | 고객 목록의 금액 열 |

## 4. 첫 Sites 요청에는 목적과 핵심 조건을 담는다

Sites의 첫 결과는 요청의 구체성에 크게 좌우된다. 화면 이름만 나열하기보다 **레이아웃, 데이터, 핵심 동작, 상태, 반응형 조건**을 함께 제공한다. 모든 세부 디자인을 처음부터 확정하려는 것이 아니라 첫 Preview가 업무 목적에 맞는 방향으로 나오게 하는 수준이면 충분하다.

다음과 같은 구성으로 작성하면 빠뜨리는 항목이 줄어든다.

```text
1. 사이트 목적
2. 전체 레이아웃
3. 카드별 정보와 크기
4. 데이터 API와 필드 매핑
5. 클릭과 필터 동작
6. 로딩, 실패, 검색 결과 없음 상태
7. 모바일 대응
8. 배포 전 확인 조건
```

예시 첫 요청은 다음과 같다.

```text
Google Sheets 데이터를 조회하는 업무 현황 대시보드를 만들어줘.

전체 구조
- 왼쪽에는 고정 사이드바를 두고 대시보드, 고객 관리,
  Google Sheets 메뉴를 배치한다.
- 오른쪽 본문에는 제목, 최근 업데이트 시각, 업무 요약,
  업무 상태 카드, 담당자별 현황 카드, 고객 목록을 배치한다.
- 본문 최대 너비는 넓은 화면에서 일정하게 유지한다.

데이터
- EXAMPLE_API_URL을 GET 방식으로 호출한다.
- 응답은 { ok, rows } 구조다.
- 사업장은 고객사명, 담당자는 담당자명,
  업무상태는 상태, 구분은 구분, 금액은 금액으로 사용한다.
- 요청에는 캐시된 이전 응답을 강제로 사용하지 않는다.

업무 상태
- 자료 수취, 작업 완료, 검토 완료, 승인 완료,
  수취 대기의 다섯 상태를 사용한다.
- 상태별 색상은 원형 차트, 범례, 누적 막대,
  테이블 태그에서 일관되게 사용한다.

상호작용
- 원형 차트 조각이나 범례를 클릭하면 고객 목록을 필터링한다.
- 같은 상태를 한 번 더 클릭하면 해당 필터를 해제한다.
- 담당자 이름이나 막대를 클릭하면 담당자로 필터링한다.
- 같은 담당자를 다시 클릭하면 해당 필터를 해제한다.
- 선택된 필터는 고객 관리 제목 옆 태그로 표시한다.
- 각 태그의 X 버튼으로 해당 필터만 해제할 수 있게 한다.
- 별도의 필터해제 버튼은 만들지 않는다.
- 고객사 검색은 선택된 필터와 동시에 적용한다.

초기 상태
- API 응답 전에는 샘플 데이터를 보여주지 않는다.
- 데이터를 조회하는 동안 Loading State를 표시한다.
- 실패 시 다시 불러오기 버튼을 제공한다.
- 실제 조회 결과가 0건이면 Empty State를 표시한다.

반응형
- 좁은 화면에서는 두 대시보드 카드를 한 열로 쌓는다.
- 검색창과 고객 목록이 화면 밖으로 넘치지 않게 한다.
```

이 요청은 디자인을 픽셀 단위로 고정하지 않는다. 대신 사용자가 실제로 검수할 수 있는 동작과 정보 구조를 분명히 한다. 이후 세부 디자인은 Preview를 보면서 좁혀 간다.

## 5. Sites가 만든 첫 화면을 Preview에서 확인한다

Sites는 생성한 사이트의 비공개 Preview를 제공한다. 첫 화면이 생성되면 바로 Publish하지 말고 실제 데이터가 연결되는지 먼저 확인한다. OpenAI의 [Sites 공식 가이드](https://help.openai.com/en/articles/20001339-creating-and-managing-chatgpt-sites)도 생성된 Preview를 검토하고 필요한 변경을 요청한 뒤 게시하도록 안내한다.

첫 검수에서는 장식보다 다음 순서를 본다.

1. API 응답 전 샘플 데이터 대신 Loading State가 보이는지 확인한다.
2. Google Sheets의 실제 행 수와 화면 전체 건수가 같은지 확인한다.
3. 상태별 합계의 총합이 전체 건수와 같은지 확인한다.
4. 담당자별 막대의 합계가 고객 목록과 일치하는지 확인한다.
5. 상태와 담당자 필터가 고객 목록에 적용되는지 확인한다.
6. 같은 항목을 다시 눌렀을 때 선택이 해제되는지 확인한다.
7. 검색어와 선택 필터가 동시에 적용되는지 확인한다.
8. 새로고침 후 시트의 변경 값이 반영되는지 확인한다.

> "화면 모양이 괜찮다면 데이터 검증은 배포 후 해도 되지 않는가?"

그렇지 않다. 차트가 그럴듯하게 보여도 샘플 데이터가 남아 있거나 상태명이 하나라도 다르면 집계가 틀릴 수 있다. **실제 시트의 한 행을 수정한 뒤 화면 전체가 함께 변하는지 확인하는 것**이 가장 확실한 통합 테스트다.

## 6. 기존 Site는 현재 화면을 기준으로 수정 요청한다

Sites에서 기존 Site를 편집할 때는 처음부터 전체 요구사항을 다시 설명할 필요가 없다. 현재 Preview를 기준으로 **바꾸고 싶은 부분과 원하는 결과를 자연어로 직접 설명하면 된다.**

수정 요청에는 보통 다음 세 가지를 포함하면 충분하다.

```text
1. 어디를 바꿀지
2. 어떻게 바뀌어야 하는지
3. 무엇은 그대로 유지할지
```

예를 들어 카드 레이아웃을 수정하고 싶다면 CSS나 컴포넌트 구조를 직접 지정하기보다 원하는 결과를 먼저 설명한다.

```text
업무 상태와 담당자별 현황 카드의 높이는 유지해줘.

담당자별 현황을 조금 더 넓게 배치하고,
업무 상태의 원형 차트는 카드 안의 빈 공간이
과하게 남지 않을 정도로 키워줘.

현재 전체적인 디자인과 카드 간격은 유지해줘.
```

동작을 수정할 때도 마찬가지다.

```text
업무 상태나 담당자를 클릭하면 고객 목록이 필터링되게 해줘.

현재 선택된 항목을 다시 클릭하면
해당 필터만 해제되고 다른 필터와 검색어는 유지해줘.
```

초기 화면처럼 데이터 상태를 수정할 수도 있다.

```text
Google Sheets 데이터를 불러오기 전에 표시되는
샘플 데이터는 제거해줘.

조회 중에는 Loading State를 보여주고,
조회가 완료된 후 실제 데이터를 표시해줘.
```

Sites에서는 처음부터 구현 방법까지 정확하게 지정할 필요는 없다. 우선 **사용자가 화면에서 보고 싶은 결과를 설명하고 Preview를 확인한 뒤**, 필요한 부분만 다시 좁혀 요청하는 방식이 자연스럽다.

```text
1차 요청
원형 차트를 조금 키워 카드의 빈 공간을 줄여줘.

↓ Preview 확인

2차 요청
차트 크기는 좋아.
차트와 범례 사이 간격만 조금 줄여줘.
다른 레이아웃은 그대로 유지해줘.
```

즉 Sites에 수정 요청할 때는 긴 구현 명세보다 **현재 화면에서 발견한 문제 → 원하는 결과 → 유지할 부분**을 명확하게 전달하는 것이 중요하다.

## 7. 아이콘과 문구는 식별 가능한 기준을 준다

아이콘을 다른 것으로 바꿔 달라는 요청은 결과가 모호할 수 있다. 아이콘 라이브러리와 아이콘 이름 또는 코드가 있다면 함께 전달한다.

```text
고객사 검색 아이콘은 Tabler Icons의 search 아이콘으로 바꿔줘.
크기는 18px로 맞추고 입력창 세로 중앙에 정렬해줘.
```

이미지 후보를 비교해야 한다면 먼저 여러 후보의 미리보기를 요청하고, 선택한 후보 번호를 다시 전달한다. 한 번에 생성과 배포를 요청하기보다 선택을 마친 뒤 적용하는 편이 불필요한 재배포를 줄인다.

문구 수정도 기존 문구와 변경 문구를 함께 적으면 정확하다.

```text
다음 안내 문구를 변경해줘.

기존: 상태를 클릭해 필터링하고, 한 번 더 누르면 해제할 수 있어요.
변경: 상태를 클릭해 원하는 업무만 필터링할 수 있어요.
```

마침표, 띄어쓰기, 숫자 단위처럼 작은 차이도 최종 요청에 그대로 적는다. 화면 문구는 코드보다 사용자가 더 자주 보는 인터페이스다.

## 8. 외부 API 연결은 화면 생성과 분리해 생각한다

Sites는 화면과 상호작용을 만들지만, Google Sheets의 비공개 데이터를 직접 공개해 주는 도구는 아니다. 데이터 조회 경로는 별도로 준비해야 한다.

Apps Script는 다음처럼 조회, 변환, 응답의 역할을 나눈다.

```javascript
function doGet() {
  try {
    return json_({
      ok: true,
      rows: getRows_(),
    });
  } catch (error) {
    return json_({
      ok: false,
      message: String(error),
      rows: [],
    });
  }
}

function getRows_() {
  const spreadsheet = SpreadsheetApp.openById(
    "EXAMPLE_SPREADSHEET_ID"
  );
  const sheet = spreadsheet.getSheetByName("업무현황");
  const values = sheet.getDataRange().getDisplayValues();
  const [headers, ...rows] = values;

  return rows
    .filter((row) => row.some(Boolean))
    .map((row) =>
      headers.reduce((record, header, index) => {
        record[header] = row[index] ?? "";
        return record;
      }, {})
    );
}

function json_(value) {
  return ContentService
    .createTextOutput(JSON.stringify(value))
    .setMimeType(ContentService.MimeType.JSON);
}
```

Apps Script를 다시 배포해 `/exec` 주소가 바뀌었다면 Sites에도 새 주소를 전달한다.

```text
Google Sheets 조회 API를 다음 주소로 변경해줘.
EXAMPLE_API_URL

기존 화면과 필드 매핑은 유지하고,
업데이트된 Preview에서 실제 데이터가 표시되는 것까지 확인해줘.
아직 배포하지는 마.
```

이처럼 데이터 연결을 먼저 Preview에서 확인하고, 문제가 없을 때 별도로 Publish를 요청하면 운영 화면에 오류가 반영되는 시간을 줄일 수 있다.

## 9. Publish는 Preview 검토 이후의 별도 단계다

Preview는 작업 중인 결과를 검토하는 화면이고, 다른 사용자가 접속하는 주소는 Publish된 결과다. Preview에서 정상으로 보인다고 운영 Site가 자동으로 바뀌는 것은 아니다.

[OpenAI 공식 가이드](https://help.openai.com/en/articles/20001339-creating-and-managing-chatgpt-sites)에 따르면 배포로 생성된 URL은 모두 운영용 URL이다. 라이브 Site를 바꾸지 않고 변경사항을 검토하려면 먼저 버전을 저장하고, 검토가 끝난 후 배포해야 한다.

일반적인 흐름은 다음과 같다.

```text
요구사항 전달
→ Sites가 화면 수정
→ 업데이트된 Preview 확인
→ 필요한 후속 수정
→ 검토한 버전 저장
→ Publish
→ 운영 주소 재확인
```

작업 요청 끝에 Publish까지 해달라고 명시하면 수정과 배포를 이어서 진행할 수 있다. 중요한 데이터 연결을 바꾸는 경우에는 Preview 검토와 Publish를 두 단계로 나누는 편이 안전하다.

배포 후에는 다음 항목을 다시 확인한다.

- 운영 주소에서 최신 디자인이 보이는가
- 새로고침해도 API 데이터가 정상 표시되는가
- 상태와 담당자 필터를 다시 눌러 해제할 수 있는가
- 검색 결과와 필터 결과가 함께 적용되는가
- 모바일 너비에서 카드와 표가 깨지지 않는가
- 도움말과 외부 링크가 정상적으로 열리는가

## 10. 다른 계정의 Sites에서 다시 만들려면 명세가 필요하다

Sites 프로젝트를 다른 계정에서 동일하게 재구성하려면 최종 화면만 보여주는 것으로는 부족하다. **구현 명세와 재생성 프롬프트**를 함께 남겨야 한다.

구현 명세에는 다음 정보가 필요하다.

| 구분 | 기록할 내용 |
|---|---|
| 화면 구조 | 사이드바, 상단바, 요약, 카드, 고객 목록의 배치 |
| 디자인 기준 | 색상, 간격, 카드 비율, 차트 크기, 반응형 기준 |
| 데이터 구조 | API 응답 예시와 필드 매핑 |
| 계산 규칙 | 완료, 미완료, 완료율, 상태별 건수 계산법 |
| 상호작용 | 필터 선택, 재선택 해제, 태그 X, 검색 결합 |
| 상태 화면 | 로딩, 실패, 검색 결과 없음 |
| 외부 의존성 | Apps Script API, 원본 시트 링크, 아이콘 출처 |
| 검수 조건 | 실제 데이터 합계와 화면 합계의 일치 여부 |

재생성 프롬프트에는 최종 결과만 쓰지 말고 선택과 해제의 조건을 함께 쓴다.

```text
선택된 상태를 다시 클릭하면 상태 필터만 해제한다.
상태 태그의 X를 누르면 담당자 필터와 검색어는 유지한다.
API 응답 전에는 샘플 데이터를 렌더링하지 않는다.
담당자별 현황 카드는 업무 상태 카드보다 약간 넓게 만든다.
두 카드의 높이는 자연스럽게 맞춘다.
```

이런 문장은 화면의 모양이 아니라 **업무 규칙**을 보존한다. 다른 계정에서 다시 생성해도 동작 차이가 줄어든다.

## 11. Sites 접근 제한과 API 보안은 별개다

Sites에서 사이트 공개 범위를 제한하더라도 Apps Script Web App이 모든 사용자에게 공개되어 있다면 API 주소를 아는 사용자가 직접 호출할 수 있다.

```text
Sites 접근 제한
└─ 대시보드 화면을 누가 볼 수 있는가

Apps Script 접근 제한
└─ 원본 데이터 API를 누가 호출할 수 있는가
```

> "사이트를 비공개로 만들면 Google Sheets 데이터도 자동으로 보호되는가?"

그렇지 않다. 화면 권한과 API 권한은 각각 설계해야 한다.

개인 계정에서 여러 외부 ChatGPT 계정을 허용하려는 경우에도 Sites의 공유 범위가 원하는 방식의 계정 목록을 지원하는지 먼저 확인해야 한다. 지원되지 않는 계정 단위 제어가 필요하면 로그인 기능이 있는 별도 배포 구조나 인증 프록시를 검토해야 한다.

민감한 데이터라면 최소한 다음을 확인한다.

- Apps Script가 모든 사용자에게 공개되어도 되는 데이터인가
- API 응답에 불필요한 개인정보가 포함되어 있지 않은가
- 허용 사용자 검증이 API 호출 단계에도 적용되는가
- 사이트 주소와 API 주소가 로그나 문서에 불필요하게 노출되지 않는가

---

## 12. 정리

Sites로 업무 대시보드를 만드는 핵심은 프런트엔드 코드를 직접 작성하는 데 있지 않다. **현재 결과를 보고 수정 대상, 기대 결과, 유지 조건을 자연어로 전달하며 Preview와 Publish 흐름을 잘 사용하는 데 있다.**

- 첫 요청에는 목적, 레이아웃, 데이터, 상호작용, 상태 화면을 함께 적는다.
- Google Sheets는 Apps Script 조회 API를 통해 연결한다.
- 같은 UX 목적은 묶어도 되지만 관련 없는 변경은 Preview 검수를 위해 나눈다.
- 데이터 연결 변경은 Preview에서 확인한 뒤 Publish한다.
- Sites 화면 접근 제한과 Apps Script API 보안은 별도로 설계한다.

Sites는 요구사항을 빠르게 실제 화면으로 바꾸는 데 강점이 있다. 그 강점을 살리려면 한 번의 긴 명세로 완성하려 하기보다 **현재 결과를 보고 변경을 요청하고, Preview에서 확인한 뒤 다음 수정 범위를 좁혀 가야 한다.**
