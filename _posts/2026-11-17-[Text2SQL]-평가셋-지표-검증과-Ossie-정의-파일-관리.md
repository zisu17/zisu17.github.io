## 1. 배경

Text2SQL 스터디에서 Olist 데이터를 기준으로 공통 평가셋 49문항을 만들었다. 각 문항에는 질문과 함께 조회 기간, 주문 상태, 분모처럼 계산에 필요한 조건이 들어 있다. 정답 SQL과 결과 표도 같이 준비했다.

앞서 [시맨틱 정의를 관리하는 방식](/data/text2sql-ossie-graphrag-semantic-layer-governance/)을 설계하고 [Claude Code·Codex 플러그인](/data/text2sql-agent-claude-codex-plugin/)에서 그 정의를 사용하도록 구성했다. 이번에는 시맨틱 정의가 있을 때 Text2SQL 정답률이 달라지는지 확인하고 싶었다. 그러려면 먼저 평가셋에서 묻는 지표를 정의하고 계산 결과가 정답 표와 맞는지 확인해야 했다.

처음에는 실험에 쓸 지표를 하나씩 추가하기 편하도록 지표마다 파일을 만들었다. 그런데 여러 지표를 함께 쓰는 문항을 처리하기 어려웠고 같은 테이블 관계를 파일마다 관리해야 했다.

## 2. 평가 문항을 지표에 매핑하기

플러그인에서 집계 질문을 받으면 모델이 지표, 그룹화 기준, 필터를 고른다. SQL은 `t2s compile`이 정의를 바탕으로 생성한다. 당시 엔진은 정의된 다대일 관계를 따라 조인하고 지표 계산식에 서브쿼리나 윈도 함수를 허용하지 않았다.

먼저 문항별로 지표를 재사용할 수 있는지 확인했다. 예를 들어 결제 금액과 배송 지연 건수는 집계식으로 정의할 수 있다. 반면 고객별 첫 구매일을 구한 뒤 재구매를 판정하거나 주문별로 마지막 리뷰를 고르는 문제는 한 번의 지표 집계로 답하기 어려워 별도로 분류했다.

기존 매출·배송비·주문 수 지표를 재사용하고 다음 지표 17개를 추가했다.

| 집계 기준 | 새로 정의한 지표 |
|---|---|
| 결제 | 결제 금액, 결제 건수, 평균 할부 개월 수 |
| 주문 | 전체 주문 수 |
| 배송 완료 주문 | 배송 지연 비율, 지연 판정 대상 주문 수, 지연 주문 수, 평균 배송 일수 |
| 고객 | 구매 고객 수 |
| 판매자·상품 | 판매자 수, 등록 상품 수 |
| 리뷰 | 리뷰 수, 불만 리뷰 비율, 리뷰 답변 평균 일수 |
| 주문 상품 | 주문 상품 행 수, 판매자·고객이 같은 주에 속한 비율, 발송 기한 준수율 |

지표 자체에 둘 조건과 질문마다 달라지는 조건은 나눴다. 결제 금액을 묻는 문항 중 하나는 2017년 배송 완료 주문만 집계했고 다른 문항은 기간이나 주문 상태를 제한하지 않았다. 그래서 지표에는 해당 조건을 넣지 않고 필요한 문항에서만 필터로 적용했다.

평균 배송 일수는 계산 방식이 달라 별도 지표를 만들었다. 기존 지표는 날짜 차이를 썼지만 평가 문항은 구매 시각부터 도착 시각까지의 시간을 일 단위로 환산해 소수점까지 구해야 했다. 기존 매출과 주문 수는 취소·재고 없음 주문을 제외하지만 결제 지표는 주문 상태를 제한하지 않는다. 이렇게 대상이 다른 지표로 비율을 계산할 때는 분자와 분모의 주문 상태 조건을 맞춰야 한다.

## 3. 지표 계산 결과 검증

새 지표는 승인 전 상태로 추가했다. `t2s check`로 정의와 DB 값을 검사한 뒤 `t2s compile --allow-draft --run`으로 문항의 조건을 넣어 미리 계산했다. 정답 표와 일치하면 승인하고 다시 검사했다. 지표마다 확인한 정답 값 하나는 `expected`에 남겨 이후 계산식이 바뀌어도 허용 오차를 벗어나는지 확인할 수 있게 했다.

미리 보기에서는 `--by`와 `--where` 값을 사람이 넣었고 승인 전 조인 관계도 사용할 수 있었다. 따라서 이 단계에서 확인한 것은 계산식과 결과가 맞는지였다. 모델이 같은 지표와 조건을 고르는지와 승인된 정의만으로 계산할 수 있는지는 별도로 봐야 했다.

### 계산식 조건과 기준 테이블

계산식을 작성하면서 `AND`를 넣은 지표가 검사에서 거절됐다. [SQLGlot의 `AND` 노드](https://sqlglot.com/sqlglot/expressions/core.html#And)는 함수 노드로도 분류되는데 당시 `t2s`의 지표 계산식 검사에서는 허용 목록에 없었다. 계산식 안의 조건은 `CASE WHEN`을 중첩해 표현했다. SQL 자체에서 `AND`를 쓸 수 없다는 뜻은 아니다.

구매 고객 수는 기준 테이블에 따라 결과가 달라졌다. 고객 ID의 `COUNT(DISTINCT ...)`는 행이 중복돼도 값이 같아서 당시 엔진은 조인이 적은 `orders`를 기준 테이블로 골랐다. 주문 상태만 확인하니 상품이 담기지 않은 주문의 고객도 포함됐다. `order_items`의 컬럼을 조건에 추가해 상품이 있는 주문만 세도록 했다.

```sql
-- 기간 조건 생략
SELECT COUNT(DISTINCT CASE
  WHEN order_items.order_id IS NULL THEN NULL
  WHEN orders.order_status IN ('canceled', 'unavailable') THEN NULL
  ELSE customers.customer_unique_id
END) AS purchasing_customers
FROM order_items
LEFT JOIN orders ON order_items.order_id = orders.order_id
LEFT JOIN customers ON orders.customer_id = customers.customer_id;
```

2018년 2월 구매 고객 수는 6,469명에서 정답인 6,468명으로 바뀌었다. 월·카테고리별 정답 표 485행의 고객 수 값 970개도 모두 일치했다. 판매자·고객이 같은 주에 속한 비율과 발송 기한 준수율도 분자와 분모를 주문 상품 단위로 맞췄다.

## 4. 지표별 파일에서 단일 YAML로 돌아온 이유

### 지표별로 나눈 파일의 문제

처음에는 지표마다 별도 Ossie 파일을 만들고 계산에 필요한 테이블과 조인 관계를 같이 넣었다. `t2s`는 한 번에 정의 파일 하나를 사용했고 이 구성에서는 다른 파일에 있는 공통 정의를 참조할 수 없었다. 예를 들어 결제 금액 파일과 결제 건수 파일에 모두 결제와 주문의 조인 관계가 들어갔다.

지표를 작성한 맥락 없이 정의 파일과 평가셋만 넘겨 다시 검토해 보니 계산식은 맞았지만 파일을 나눠서 생긴 문제가 있었다.

- 새 지표가 필요한 19문항 중 11문항에는 지표가 둘 이상 필요했다. 결제 금액과 결제 건수를 함께 묻는 경우처럼 지표 하나만 들어 있는 파일로는 정답 표를 만들 수 없었다. 정의 파일을 사용하면 별도 집계 SQL도 제한되므로 빠진 열을 직접 계산할 수도 없었다.
- 같은 조인 관계 3개가 기존 파일에서는 승인 전이었지만 지표별 파일 7곳에서는 승인 상태였다. 기존 파일로 영문 카테고리나 판매자 주별 결과를 구하는 6문항은 필요한 조인을 사용할 수 없었다.

### 공통 파일을 두고 실행 전에 합치기

테이블과 조인 관계는 `common.ossie.yaml`에 모으고 지표 22개는 `metrics/` 아래 조각 파일로 분리했다. 스크립트가 두 종류의 파일을 합쳐 `build/`에 완성된 Ossie YAML을 만든다. 합친 파일에서 승인된 정의만 사용해 20문항을 다시 계산했고 정답 표와 일치했다. 지표가 2~4개 필요한 문항도 `t2s compile` 한 번으로 계산할 수 있었다.

문제는 기존 도구가 완성된 Ossie 파일을 기준으로 동작한다는 점이었다. 지표 조각은 필수 필드가 없어 [Ossie 공식 검증기](https://github.com/apache/ossie/blob/main/validation/validate.py)를 단독으로 통과할 수 없었다. 조각을 수정해도 정의 검사 훅이 실행되지 않았고 지표 정의 스킬이 합친 파일을 직접 고치면 다음 빌드에서 수정이 사라졌다. 그래프 적재기는 정의 파일이 있는 디렉터리 이름을 테넌트로 사용해 `build`를 테넌트로 인식했다.

원래 설계는 Git에 있는 Ossie YAML을 기준으로 두고 그래프는 그 파일에서 다시 만드는 방식이었다. 조각을 관리하면 Git에는 개별 조각만 남고 실제로 검증하고 사용하는 Ossie 파일은 `build/`에만 생긴다. 테이블 8개와 지표 22개를 한 사람이 편집하는 규모라 정의 파일을 나눠 얻는 이점보다 검증과 적재 도구를 수정해야 하는 범위가 더 컸다.

### 기준 파일과 실험용 파일 분리

테이블 8개, 조인 관계 7개, 지표 22개와 승인 상태를 `sales.ossie.yaml` 하나에 담았다. 이 파일은 Git에서 관리하고 Ossie 공식 검증과 DB 대조를 거쳤다. 실험에서 일부 지표만 사용하고 싶을 때는 기준 파일을 고치는 대신 `pick_metrics.py`로 별도 파일을 만든다.

```text
definitions/olist/sales.ossie.yaml  # Git에서 관리하는 전체 정의
build/sales.picked.ossie.yaml       # 선택한 지표만 담은 실험용 파일
```

실험용 파일은 모델 이름에 `_picked`를 붙이고 설명에 포함한 지표 이름을 남긴다. 답변 기록에서 어떤 지표를 사용했는지 확인할 수 있다. 지표를 실험에서 제외할 때도 승인 상태는 바꾸지 않는다. 승인 여부는 사람이 검토한 결과이고 실험에 포함할지는 별개의 조건이기 때문이다.

## 5. 49문항 지원 범위와 정답률 평가

최종 정의 파일에서 승인된 지표를 사용해 문항별 계산 결과를 정답 표와 대조했다. 지표와 조건은 직접 지정했고 소수 값은 정답 표의 반올림 자리에 맞춰 비교했다. 정답 표에서 값 하나를 바꿨을 때 비교 스크립트가 차이를 잡는지도 확인했다.

| 지원 범위 | 문항 수 |
|---|---:|
| 지표 계산 한 번으로 정답 표 생성 | 14 |
| 필요한 지표 값은 모두 나오지만 정답 표를 만들려면 후처리 필요 | 13 |
| 일부 열만 지표로 계산 가능 | 2 |
| 현재 지표 구조로는 계산할 수 없어 별도 SQL 필요 | 20 |
| 합계 | 49 |

지표로 정답 표의 모든 열에 필요한 값을 구할 수 있었던 문항은 27개다. 이 중 13개는 전년 동월 대비 증감률, 지표 간 나눗셈, 그룹별 1위 선택 같은 후처리가 필요했다. 사람이 지표와 조건을 골라 대조한 결과이므로 모델의 정답률은 아니다.

시맨틱 정의가 없는 기준 모델은 3회 평균 49문항 중 41.0문항을 맞혔다. 그런데 같은 정답 SQL 49개를 `t2s validate`로 검사하니 정의 파일이 없을 때는 모두 통과했고 정의 파일을 사용했을 때는 모두 집계 정책에 걸렸다. 현재 구성은 정의가 등록되어 있으면 집계를 지표로만 실행하도록 제한한다. 따라서 두 방식을 그대로 비교하면 정의가 답변에 준 효과뿐 아니라 허용한 SQL 범위의 차이도 점수에 반영된다. 정의를 넣은 모델의 정답률은 아직 측정하지 않았다.

같은 49문항의 조건을 보고 지표를 정의했으므로 이 평가셋으로는 처음 보는 질문에도 도움이 되는지 판단하기 어렵다. 기존 문항은 정의가 의도대로 적용되는지 확인하는 회귀 테스트로 쓰고 일반화 여부는 정의를 만들 때 사용하지 않은 문항으로 검증하는 방안을 검토하고 있다. 지표로 답할 수 있는 문항만 비교할지 아니면 정의에 없는 집계를 허용하되 별도로 표시할지도 아직 결정하지 않았다.
