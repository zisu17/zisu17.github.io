## 1. 이 글의 목적

1편에서 만든 업무 현황판에는 예시 데이터가 들어 있다. 실제로 사용하려면 Google Sheets의 행이 추가되거나 바뀔 때 사이트도 같은 내용을 보여 줘야 한다.

Sites에는 자체 저장소를 붙일 수 있지만, 이미 시트로 업무를 관리하고 있다면 데이터를 옮길 이유가 없다. 이 글에서는 **Google Apps Script를 조회 창구로 사용해 시트 데이터를 Sites에 전달하는 방식**을 다룬다.

업무 현황표를 예시로 들지만 출석부, 재고 목록, 예약 현황처럼 행과 열로 관리하는 데이터에도 같은 구조를 적용할 수 있다. 시트명과 열 이름은 모두 예시 값이다.

---

## 2. 사이트가 시트를 직접 읽게 하지 않는다

Google Sheets는 팀 안에서만 편집하는 문서다. 공개 사이트가 이 문서에 직접 접근하도록 만들면 권한 관리가 복잡해지고, 화면에 쓰지 않는 열까지 노출할 수 있다.

그래서 중간에 필요한 값만 돌려주는 조회 창구를 둔다.

```text
Google Sheets
→ Apps Script 웹 앱
→ Sites에서 만든 웹사이트
```

Apps Script는 시트를 읽어 JSON 같은 웹 데이터로 바꿔 준다. 사이트는 이 주소를 호출해 목록과 차트를 갱신한다.

여기서 중요한 점이 하나 있다. 시트가 비공개라고 해서 조회 창구까지 자동으로 비공개가 되는 것은 아니다. 로그인하지 않은 방문자도 보는 사이트라면 창구 역시 외부 요청을 받을 수 있어야 한다. 따라서 **창구에서 내보낼 열을 처음부터 제한해야 한다.**

---

## 3. 먼저 시트를 정리한다

사람이 보기 편한 표가 프로그램에도 읽기 좋은 것은 아니다. 연결 전에 시트를 단순한 표로 정리한다.

| 확인할 항목 | 이유 |
|---|---|
| 첫 행에는 열 이름만 둔다 | 각 값의 이름표로 사용한다 |
| 표 안에서는 셀을 병합하지 않는다 | 병합된 행은 일부 값이 빈칸으로 읽힌다 |
| 상태와 구분의 표기를 통일한다 | `완료`와 `완료됨`은 서로 다른 값이다 |
| 중간의 빈 행을 없앤다 | 데이터 범위를 잘못 판단할 수 있다 |
| 공개하지 않을 열을 정한다 | 연락처와 내부 메모가 함께 전달되는 일을 막는다 |

상태처럼 집계에 사용하는 열은 드롭다운으로 선택지를 고정하는 것이 좋다. 띄어쓰기 하나만 달라도 차트에서는 별도 항목으로 잡힌다.

예시 시트의 첫 행은 다음 정도면 충분하다.

```text
업무명 | 담당자 | 구분 | 상태 | 기준일
```

---

## 4. Apps Script로 조회 주소를 만든다

Google Sheets에서 **확장 프로그램 > Apps Script**를 열고, 시트를 읽어 웹 응답으로 돌려주는 코드를 만든다. 코드를 직접 작성하기 어렵다면 Sites나 ChatGPT에 시트 구조와 출력 조건을 알려 주고 초안을 받을 수 있다.

```text
Google Sheets 데이터를 조회하는 Apps Script 웹 앱 코드를 만들어 줘.

- 시트 이름은 업무현황이야.
- 첫 행에는 업무명, 담당자, 구분, 상태, 기준일이 있어.
- 값이 없는 행은 제외해 줘.
- 연락처와 내부 메모 열은 응답에 포함하지 마.
- 날짜는 YYYY-MM-DD 형식으로 보내 줘.
- GET 요청에 JSON으로 응답해 줘.
- 오류가 나면 원인을 확인할 수 있는 메시지를 남겨 줘.
```

코드를 붙여 넣고 저장한 뒤 웹 앱으로 배포한다. 메뉴 이름과 접근 권한 항목은 Google 계정 종류에 따라 조금씩 다를 수 있다.

배포할 때는 다음 두 가지를 확인한다.

- 실행 주체: 시트를 읽을 권한이 있는 계정
- 접근 범위: Sites의 방문 방식에 맞는 범위

공개 사이트에서 로그인 없이 데이터를 불러오려면 조회 주소도 외부 요청을 받아야 한다. 이 설정은 편리하지만, 주소를 아는 사람이 응답을 직접 읽을 수 있다는 뜻이기도 하다.

배포가 끝나면 보통 `/exec`로 끝나는 URL이 생긴다. 브라우저에서 열어 보고 시트 전체가 아니라 의도한 열만 나오는지 먼저 확인한다.

시트의 셀 값만 바꾼 경우에는 다시 배포하지 않아도 된다. Apps Script 코드를 수정한 경우에는 새 버전으로 다시 배포해야 변경 사항이 반영된다.

## 5. Sites에 데이터 연결을 요청한다

조회 URL만 전달하면 어떤 값을 어느 화면에 써야 하는지 다시 추측하게 된다. 응답의 열과 화면 요소를 함께 지정한다.

```text
이 조회 주소의 데이터를 업무 현황판에 연결해 줘.
(Apps Script 웹 앱 URL)

- 업무명과 담당자와 상태는 아래쪽 목록에 표시해 줘.
- 상태는 위쪽 요약 숫자와 상태별 차트 계산에 사용해 줘.
- 담당자는 담당자별 업무량 차트에 사용해 줘.
- 화면을 열 때 최신 데이터를 불러와 줘.
- 불러오는 동안에는 로딩 상태를 보여 줘.
- 요청이 실패하면 오류 안내와 다시 시도 버튼을 보여 줘.
- 데이터가 0건이면 빈 화면 안내를 보여 줘.
- 아직 배포하지 말고 검토할 버전만 저장해 줘.
```

연결 주소에 인증 정보나 비밀 값이 포함되어 있다면 프롬프트나 소스 코드에 직접 넣지 않는다. Sites 설정의 환경 값으로 관리하고, 서버 쪽에서 읽도록 요청해야 한다.

---

## 6. 화면보다 숫자를 먼저 맞춘다

차트는 데이터가 조금 빠져도 멀쩡해 보인다. 그래서 연결 직후에는 디자인보다 집계 결과를 확인해야 한다.

1. 시트의 유효한 행 수와 화면의 전체 건수가 같은지 본다.
2. 상태별 건수를 더해 전체 건수와 같은지 확인한다.
3. 빈 상태나 예상하지 못한 상태명이 없는지 찾는다.
4. 날짜와 숫자 형식이 의도대로 표시되는지 본다.
5. 시트의 한 행을 바꾼 뒤 새로고침해 화면도 바뀌는지 확인한다.

숫자가 맞지 않으면 먼저 시트를 본다. 셀 끝의 공백, 서로 다른 상태명, 수식이 빈 문자열을 반환하는 행, 병합된 셀이 흔한 원인이다.

사이트에서 별도로 필터링하거나 합계를 계산한다면 그 규칙도 확인한다. 예를 들어 `완료`만 완료 건수에 넣을지, `검수 완료`까지 포함할지 기준이 있어야 한다.

---

## 7. 공개 범위는 두 곳에서 확인한다

이 구성에는 접근 범위가 두 개 있다.

```text
Sites의 공유 설정
└─ 누가 화면을 볼 수 있는가

Apps Script의 접근 설정
└─ 누가 원본 응답을 받을 수 있는가
```

Sites를 특정 사용자에게만 공유해도 Apps Script 웹 앱이 공개 상태라면, 조회 URL을 아는 사람은 데이터를 직접 요청할 수 있다. 사이트를 잠갔다고 데이터 창구까지 잠기는 것은 아니다.

따라서 공개 전에 다음을 확인한다.

- 응답에 연락처, 내부 메모, 식별번호가 들어 있지 않은가
- 사이트에 쓰지 않는 열까지 보내고 있지 않은가
- 실명 대신 별칭으로 바꿔도 되는가
- 공개 URL만으로 조회할 수 있는 데이터인가

민감한 데이터에 단순 공개 Apps Script 웹 앱을 쓰는 것은 맞지 않는다. 인증이 필요하다면 로그인과 권한 검사를 포함한 별도 API를 사용하거나, 데이터 자체를 공개 가능한 형태로 가공해야 한다.

화면에서 열을 숨기는 것만으로는 충분하지 않다. 브라우저에 응답이 도착했다면 화면에 보이지 않아도 데이터는 전달된 것이다. 제외할 값은 Apps Script가 응답을 만들 때부터 빼야 한다.

---

## 8. 2편 요약

- 기존 시트를 계속 사용하려면 Apps Script 웹 앱을 조회 창구로 둘 수 있다.
- 연결 전에 첫 행, 병합 셀, 빈 행, 상태 표기를 정리한다.
- Apps Script 응답에는 사이트에서 실제로 쓸 열만 넣는다.
- Sites에는 열과 화면 요소의 대응 관계, 로딩, 오류, 빈 화면 동작을 함께 요청한다.
- 연결 결과는 차트 모양보다 행 수와 상태별 합계로 검증한다.
- Sites의 공유 범위와 Apps Script의 접근 범위는 따로 관리한다.

Google Sheets는 입력 화면으로 남고, Sites는 데이터를 보여 주는 화면이 된다. 연결 자체보다 중요한 것은 어떤 데이터를 어디까지 공개할지 먼저 정하는 일이다.
