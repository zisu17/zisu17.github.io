## CDC의 개념

운영 DB의 주문 상태가 바뀌었을 때 분석용 DB나 검색 시스템에도 같은 변경을 반영하고 싶을 수 있다. 매번 전체 테이블을 다시 읽는 대신 바뀐 데이터를 따라가는 방법이 CDC(Change Data Capture)이다.

CDC는 데이터의 삽입과 수정, 삭제를 감지해 다른 시스템으로 전달하는 방식이다. 얼마나 빨리 반영되는지와 어떤 변경을 감지할 수 있는지는 구현 방식에 따라 달라진다.

![소스 DB의 변경 사항을 다른 시스템에 반영하는 CDC 구조](https://github.com/zisu17/zisu17/assets/108858121/428a853a-28da-4071-8e0c-9bea1212535a)

예를 들어 주문 `101`의 상태가 `created`에서 `paid`로 바뀌면 대상 시스템에서도 주문 `101`을 찾아 상태를 바꾸어야 한다. 변경 이벤트를 가져오는 것과 대상에 올바르게 적용하는 것은 나누어 생각해야 한다.

## 주기적으로 조회해서 변경 찾기

가장 간단하게는 수정 시각이나 증가하는 ID를 기준으로 DB를 반복 조회할 수 있다.

```sql
SELECT id, status, updated_at
FROM orders
WHERE updated_at >= :last_checked_at;
```

`:last_checked_at`은 애플리케이션이 전달할 조회 기준값이다. 실제 파라미터 표기는 사용하는 DB 드라이버에 맞춘다.

이 방식은 익숙한 SQL로 구현할 수 있지만 조회 간격만큼 반영이 늦어질 수 있다. 인덱스와 조회 범위에 따라 원본 DB에 부하도 생긴다.

또 `updated_at`이 없는 변경이나 물리적으로 삭제된 행은 이 쿼리만으로 찾기 어렵다. 같은 수정 시각을 가진 행과 조회 도중 변경되는 데이터도 고려해야 한다. 단순히 마지막 시각 하나만 저장하면 경계에 있는 변경을 빠뜨릴 수 있다.

## 로그에서 변경 찾기

로그 기반 CDC는 DB가 기록한 변경 로그를 이용한다. PostgreSQL에서는 WAL(Write-Ahead Log)을 논리적으로 디코딩해 행 변경을 읽는 방식을 사용할 수 있다.

대상 테이블을 매번 전체 조회하지 않아도 된다는 장점이 있다. 그렇다고 원본 DB에 부하가 없는 것은 아니다. WAL 생성과 디코딩, 네트워크 전송과 로그 보관에 자원이 필요하다.

| 구분 | 주기적 조회 | 로그 기반 CDC |
|---|---|---|
| 변경을 찾는 곳 | 테이블의 현재 값 | DB 변경 로그 |
| 삭제 감지 | 삭제 표시 등 별도 설계 필요 | 지원하는 변경 이벤트로 전달 가능 |
| 초기 준비 | 조회 기준과 인덱스 준비 | DB 설정과 권한·복제 슬롯 등 준비 |
| 중단 후 재개 | 저장한 조회 기준 사용 | 저장한 로그 위치와 남아 있는 로그 사용 |

로그 기반이라고 무조건 모든 테이블의 모든 변경을 가져오는 것은 아니다. Connector의 테이블 선택과 publication 설정, 변경 유형 지원 범위에 따라 달라진다.

## Debezium과 Kafka의 역할

Debezium은 DB의 변경을 읽어 이벤트로 만드는 CDC 도구이다. 여기서는 PostgreSQL Connector를 Kafka Connect에서 실행하는 구성을 사용한다. Kafka를 사용하지 않는 배포 방식도 있지만 이 시리즈의 구성과는 구분한다.

![Debezium과 Kafka를 거쳐 변경 데이터를 전달하는 구조](https://github.com/zisu17/zisu17/assets/108858121/e2d52ff8-4250-4353-9c28-6872c432ff9e)

```text
PostgreSQL → Debezium Source Connector → Kafka 토픽
Kafka 토픽 → Consumer 또는 Sink Connector → 대상 시스템
```

Debezium이 PostgreSQL의 로그 위치를 관리하고 Kafka는 전달된 이벤트를 보관한다. Kafka의 오프셋은 토픽 파티션 안의 위치이고 PostgreSQL의 LSN은 WAL 안의 위치이다. 둘은 서로 다른 값이다.

### 초기 데이터와 이후 변경

이미 데이터가 있는 DB라면 로그를 읽는 것만으로 기존 행 전체를 가져올 수는 없다. 일반적인 초기 구성에서는 스냅샷으로 기존 행을 읽고 그 뒤 변경 로그를 이어서 처리한다.

예를 들어 스냅샷에서 주문 `101`을 읽은 뒤 상태 변경 이벤트를 적용해 최종 값을 맞춘다. 스냅샷과 변경 로그 사이의 일관성을 어떻게 보장하는지는 Connector가 사용하는 방식과 설정을 확인해야 한다.

### 대상 시스템이 잠시 멈추면

대상 시스템이 멈춰도 Kafka에 필요한 이벤트가 남아 있다면 Consumer가 저장한 오프셋부터 다시 읽을 수 있다. 이때 보존 기간이나 용량 제한으로 이벤트가 이미 지워졌다면 같은 방법으로 복구할 수 없다.

DB에서 Kafka로 보내는 구간도 별도로 확인해야 한다. Connector가 오래 멈추면 PostgreSQL의 복제 슬롯 때문에 WAL이 계속 쌓일 수 있고 필요한 WAL이 제거되면 재스냅샷이 필요할 수 있다.

재시작 과정에서 같은 변경을 다시 받을 가능성도 고려한다. 대상 시스템은 기본 키를 기준으로 upsert하거나 처리한 이벤트를 구분하는 등 중복 적용에 대비해야 한다. Kafka에 전달했다는 이유만으로 전체 파이프라인이 한 번만 처리된다고 보장되지는 않는다.

## 구성할 때 확인할 순서

1. PostgreSQL에서 논리 디코딩 설정과 대상 테이블의 권한을 준비한다.
2. Kafka와 Kafka Connect를 실행하고 Debezium PostgreSQL Connector를 설치한다.
3. DB 접속 정보와 슬롯·publication·대상 테이블을 설정한다.
4. 초기 스냅샷과 이후 변경 이벤트가 토픽에 들어오는지 확인한다.
5. Consumer나 Sink Connector에서 삽입·수정·삭제를 대상에 적용한다.
6. 양쪽 구간의 지연과 오류, Kafka 보존 기간과 DB의 WAL 사용량을 확인한다.

기존 실습에서는 ZooKeeper 기반 Kafka를 사용했다. Kafka의 메타데이터 관리 방식과 Java 요구 사항은 설치할 버전의 문서를 따로 확인한다.
